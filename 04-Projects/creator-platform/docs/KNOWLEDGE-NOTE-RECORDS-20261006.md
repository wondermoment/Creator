# 笔记并发实测与逐条存储修复 · 2026-10-06

## 实测发现

上轮 Web Locks + localStorage 整数组读改写通过了合成 LockManager 回归，但本轮原生 Edge Chromium 测试出现丢记录：保留 5 条基础数据后，两页各追加 10 条，预期 25 条，复测两页均只读到 23 条，缺少 batch-A-7、batch-A-8。因此不能把上轮合成测试通过作为并发覆盖风险已经解决的证据。

初次失败及带记录列表的复现分别保存在 `KNOWLEDGE-NOTE-LOCK-BROWSER-FIRST-20261006.json`、`KNOWLEDGE-NOTE-LOCK-BROWSER-REPRO-20261006.json`。没有归因于模型或用户操作；本次确认的是原生浏览器中原方案确实丢记录，不声称已定位浏览器内部缓存机制。

默认 Playwright Chromium 未安装，首次启动失败；随后使用现有 Edge Chromium 154.0.4258.53 的独立 headless 实例，无新浏览器安装。

## 修复

新笔记以 `wld-reading-note:<encoded-id>` 独立存储，每条只写自己的键，不再覆盖整份数组。旧 `wld-reading-notes` 数组原样保留，读取时合并新旧记录并校验内容与编号；不迁移、改写或删除旧数据。同一回复继续使用稳定 UUID 去重。

三个保存入口仍共用 Web Locks 和 5 秒排队超时，保留失败提示与草稿；独立记录键负责避免不同笔记因旧列表快照而互相覆盖。损坏的新记录和旧数组都会阻止后续保存，而不是被忽略或替换为空。按时间排序只用于展示，不作为并发正确性的依据。

版本：`book-reader.js?v=note-records-28`。旧页面须刷新才能读取新格式；旧页面只识别旧数组。不能自动删除或迁移旧数组，也不能承诺不同版本页面的所有写入互操作都已验收。

## 验证

采用 webapp-testing 工作流，脚本 `tests/knowledge-note-lock-browser.py` 创建非持久浏览器上下文。所有网络请求均被拦截；测试页面加载真实 book-reader/chat-format、从项目原样提取的 showForm/travelSave 等函数，其他页面外壳为合成夹具。真实原生 Web Locks、localStorage、表单、对话框参与执行；不是完整产品/后台端到端验收。

修复后原生浏览器测试通过；补充新标签页读取验证后再次通过，最终证据见 `KNOWLEDGE-NOTE-LOCK-BROWSER-20261006.json`：

1. 两个页面同时排队保存，旧记录及两条新笔记都保留。
2. 真实 5 秒锁等待超时撤销排队，原表单草稿保留，不发生迟到写入；手动重试成功。
3. 关闭占锁页面，另一页正常继续保存。
4. 两页交错追加 20 条全部保留；并发重复保存同一 AI 回复只增加一条。
5. 合成损坏存储未被覆盖，恢复合成存储后原草稿可保存。
6. 新标签页读到全部 27 条，旧数组原始字符串完全不变。

8 套合成回归与 JS 语法检查通过，输出见 `KNOWLEDGE-NOTE-RECORDS-CHECKS-20261006.json`。新记录编号不匹配、损坏内容也加入异常阻写回归。运行首页版本与静态文件字节一致，见 `KNOWLEDGE-NOTE-RECORDS-STATIC-20261006.json`。

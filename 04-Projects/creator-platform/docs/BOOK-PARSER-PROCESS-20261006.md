# 书籍解析独立进程与超时 · 2026-10-06

## 发现与修复

上传路由原来直接在async主线程执行pypdf读取和逐页提取，复杂文件可能阻塞其他请求，也没有解析时间上限。现在通过 `asyncio.to_thread` 调用 `book_parser.parse_book_data`，启动独立Python进程解析PDF/TXT/Markdown；解析完成后才进入原有临时文件及原子替换流程。

- 子进程最长45秒；超时由 `subprocess.run` 终止并等待该直接子进程退出，返回明确失败，原文不替换。
- 同一后台进程只允许一个解析调用，第二个请求不排队、不启动解析，返回503。这个限制不跨多个后台实例。
- 保留10MB输入、PDF不加密且最多800页、分段累计200万字符的限制；父进程复核返回结构、顺序编号、片段长度及总量后才允许写入。
- UTF-8管道传递，不建立上传文件的解析临时副本；子进程标准错误不回传用户。Windows以隐藏窗口方式启动。
- 子进程使用 `-I` 隔离启动，不继承API Key、Codex登录路径或PYTHONPATH；仅传入必要的系统环境。pypdf安装在用户site-packages，因此显式添加已安装依赖目录，不启用用户site启动或`.pth`处理。
- 文件读取后仍在finally中关闭；解析、超时、繁忙、异常输出失败均不进入原文替换。

涉及 `backend/app/book_parser.py`、`backend/app/book_chat.py`，没有前端视觉变更，也没有更改模型提示或模型配置。

## 实际验证

使用Python3.12、pypdf6.12.2、合成文件及自动清理的临时资料目录。

`backend.test_book_parser`新增9项，连同既有书籍上传/输入/引用检查共19项通过：

1. 实际独立子进程提取构造的文字PDF，保留PDF页/段；UTF-8 BOM Markdown切分结果与原逻辑一致。
2. 实际子进程拒绝损坏PDF、加密PDF；空白PDF按“未提取到文字”处理。
3. 实际启动仅休眠5秒的合成子进程，测试阈值设为0.3秒，确认超时返回且后续解析仍成功；生产阈值仍为45秒。测试未直接测量OS内存上限或所有异常退出路径。
4. 两个并发调用只有第一个启动子进程；第二个立即报告繁忙；畸形JSON和不合法片段不被接受。
5. 验证隔离启动参数、45秒上限与环境不含合成API Key、CODEX_HOME及PYTHONPATH。
6. 超时、繁忙和进程失败保留已有原文字节，上传文件关闭。
7. 慢解析替身运行时，async事件循环仍能继续调度并释放该任务。
8. 实际HTTP multipart → ASGI上传路由 → 独立PDF解析进程 → 临时资料保存成功；损坏文件替换失败后原文保持不变；不可信Origin在到达解析器前被拒绝。这不是运行8765实例或浏览器端验收。

前端 `book-reader-async.cjs` 和 `book-upload-async.cjs` 两套回归通过。没有新增真实模型调用，因为本轮只调整本地解析调度和失败处理；不把本地解析测试说成AI或医学验证。

## 如实记录的首次失败

第一轮18项中正常PDF失败，空白PDF被归为解析失败；原因是 `-I` 不会自动加载本机用户site-packages中的pypdf。查询安装位置后显式传入该依赖目录，未安装新库、未关闭隔离启动。再次18项通过，随后新增HTTP联调，最终19项通过。

## 剩余边界

这是进程分离及时间/文本量控制，不是操作系统安全沙盒：尚无子进程内存硬上限、网络/文件权限隔离、跨实例解析配额。PDF在最终文字量检查前仍可能大量分配内存，正式开放不可信上传前需进一步加固。

上传依旧没有任务ID、版本冲突保护或可靠的客户端取消接口；浏览器超时不等于服务端已取消，现有未知结果提示保留。线程中正在进行的解析不会因浏览器中断而立即停止，最多受到其自身解析超时约束。
